# ADR-0006 — Tor : arti côté client, C tor côté serveur

- **Statut** : Acceptée (validation de la Phase 0)
- **Date** : 2026-11-24

## Contexte

Masquage des IP et mode strict sans repli en clair.

## Décision

Client desktop : `arti-client` embarqué ; en mode strict, le seul `Transport` instancié est le transport Tor — il n'existe pas de chemin de code vers une connexion directe. Serveur : services onion v3 hébergés par C tor (plus éprouvé), Onionbalance pour la HA. Web : utilisable via Tor Browser sur l'adresse .onion ; la page refuse de fonctionner hors .onion si le site l'exige.

## Conséquences

+ Pas de processus Tor externe à installer sur le poste.
− Premier bootstrap Tor lent (dizaines de secondes).
− Tor peut être bloqué dans certains réseaux : ponts (bridges) configurables, mais pas de transports enfichables intégrés en Phase 3 (à évaluer).

## Mise en œuvre (Phase 3)

- Crate `msg-tor` : arti démarré dans le processus ; les connexions du
  client passent par un proxy SOCKS5 local (127.0.0.1, identifiants
  aléatoires RFC 1929). C'est une variante du « transport Tor » prévu : le
  client HTTP n'a que ce proxy comme itinéraire (proxys système ignorés),
  le WebSocket emprunte le même tunnel ; Tor absent ⇒ échec, jamais de
  connexion directe.
- Épinglage TLS de la clé publique du serveur ; pour une adresse `.onion`,
  certificat auto-signé accepté seulement si sa clé est épinglée, et HTTP
  accepté (Tor chiffre et authentifie déjà).
- Serveur : `deploy/docker/compose.onion.yaml` (service onion v3, aucun port
  publié, défenses par preuve de travail). Onionbalance : Phase 4.
- Ponts et transports enfichables : non intégrés en Phase 3.
